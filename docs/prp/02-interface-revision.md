# Bascule — Phase 2 Interface Revision

Status: **complete**
Inputs: `decisions.md` ADR-007 (evidence), `03-hardware-validation.md` (raw
capture), `00-design.md` §2.6 (the interface being revised), `01-plan.md` §3
(the `GattTransport` plumbing this builds on)
Companion: `02-ci-notes.md` (test lanes and the expected-red contract tests)

ADR-007 closed with an explicit instruction: it recorded the requirement and the
evidence but deliberately did **not** redesign `ScaleDecoder`, because "that
redesign should happen with the devil's advocate pass in the room, not bolted on
post-hoc here." This is that redesign.

`00-design.md` §2.6 carries a provisional banner pointing here. Treat this
document as superseding it for the decoder, handshake, and `DecodeEvent` model;
everything else in `00-design.md` stands unchanged.

## 1. The handshake is a state machine, not a list

### Before (`00-design.md` §2.6)

```kotlin
/** Ops the session must execute after discovery, in order. */
fun initSequence(discovered: DiscoveredServices): List<GattOp>
```

### After

```kotlin
fun beginHandshake(discovered: DiscoveredServices, context: HandshakeContext): HandshakeDirective
fun onHandshakeEvent(event: DecodeEvent): HandshakeDirective

data class HandshakeContext(
    val storedCredential: ScaleCredential?,
    val freshConsentCode: Int,
)

sealed interface HandshakeDirective {
    data class Send(val op: GattOp, val expectAckWithin: Duration) : HandshakeDirective
    data object Wait : HandshakeDirective
    data class Complete(val credential: ScaleCredential?) : HandshakeDirective
    data class Abort(val reason: String) : HandshakeDirective
}
```

**Rationale.** A `List<GattOp>` returned once, before any reply is seen, can only
express a fixed sequence. The real BF720 handshake has three branch points and
none of them are knowable at the moment the list would be produced: whether to
send Register or Consent depends on whether a credential is already stored for
this scale; the Consent write's operand is the `scaleIndex` the scale assigns in
its *reply* to Register, so it literally cannot be in a list built beforehand;
and a stored credential the scale no longer honours — its user slot deleted or
reassigned — has to fall back to registering again rather than failing the
session. `beginHandshake` chooses the opening move from what is known, and
`onHandshakeEvent` advances one step per reply. `Wait` exists so an unrelated
frame arriving mid-handshake (a stray indication, a duplicate ack) is a no-op
rather than something the session has to filter before calling in.

`HandshakeContext` rather than a bare credential parameter because the consent
code for a *new* registration is generated by the session, not the decoder: it is
credential material needing a cryptographic RNG and encrypted storage, both of
which are I/O the decoder is deliberately free of (`00-design.md` §2.6's
"performs no I/O" is what makes every failure edge a JVM unit test).
`Complete.credential` is non-null exactly when this session registered, which is
the session's signal to persist — so the decoder never touches the store and the
session never needs to know what a UCP opcode is.

## 2. `DecodeEvent`: `InitAcknowledged` is replaced, not extended

### Before

```
Ignored | InitAcknowledged | Live | Stable | Malformed | SessionComplete
```

### After

```
Ignored | RegistrationResult(scaleIndex, success) | ConsentResult(success)
        | Live | Stable | Malformed | SessionComplete
```

**Rationale.** `InitAcknowledged` is removed rather than kept alongside the two
new cases. It modelled a single undifferentiated "the handshake was acked", and
under ADR-007 there is no such event: there are two acks, they carry different
payloads (`[0x20, 0x01, 0x01, scaleIndex]` vs `[0x20, 0x02, 0x01]`), and they
drive different follow-on actions (send Consent vs. subscribe). Keeping it would
leave a case in a sealed type that nothing can ever construct, and the E6 gate
that `01-plan.md` WP-07 exists to enforce — "do not subscribe before the
handshake is acknowledged" — would be checking the wrong predicate.

`Live` is kept despite the BF720 never emitting it. That is a deliberate
asymmetry with `InitAcknowledged`: `InitAcknowledged` is *wrong* (it describes an
event that does not exist), whereas `Live` is *correct but unused by this
decoder*. `ScaleDecoder` is a pluggable interface per PRP §2's explicit v2 goal,
and a broadcast-ish scale that streams live weight needs the case. See §5 for
what this means for the stabilization work package.

## 3. Correlation: one weigh-in, one `Stable`

### Added

```kotlin
fun flush(): DecodeEvent?          // on ScaleDecoder
internal class MeasurementCorrelator(decoderId: String, clock: () -> Long)
```

**Rationale.** The captured Body Composition frame declares, in its own flags
word, that it carries neither a timestamp nor a user ID — only the paired Weight
frame does. `DecodeEvent.Stable(ScaleReading)` as originally modelled assumes
each notification is independently a complete, attributable reading. It is not.
Emitting one `Stable` per notification would produce two rows for one weigh-in,
the second of them unattributable and therefore undeliverable under either branch
of `00-design.md` §7 — a wrong-user gate defeated by a decode-layer assumption.

**Where it lives, and why:** inside the decoder, as a component
`BeurerDecoder` owns, not in `GattSession`. Emission timing here is a *protocol*
fact, not a session policy — only something that knows the SIG profile knows that
0x2A9D and 0x2A9C describe one physical event. Putting it in the session would
push per-characteristic knowledge into the layer whose whole purpose is to have
none, and would have to be re-implemented by every future decoder. `GattSession`
keeps exactly one rule, unchanged from `00-design.md` §2.1: persist on `Stable`.

**`flush()` is the cost of that choice.** A buffered weight frame whose
body-composition pair never arrives must still become a reading rather than being
lost — but the decoder has no clock of its own and does no I/O, so it cannot
decide when to give up waiting. The session calls `flush()` on `SessionComplete`,
at teardown, and — **added in the Phase 2 reconciliation (O-02)** — on the
expiry of a dedicated **E17 body-composition correlation timeout, 4 s from the
buffered Weight indication** (`00-design.md` §2.3, §2.5). That edge had to be
named because none of the existing timers can fire in this state: E7's 45 s is
satisfied by the *first* frame, post-emission idle counts from an `EMITTED` that
by construction has not happened, and the only remaining backstop was the 90 s
hard ceiling — whose recovery is `TEARDOWN`, under an E8 rule that says partial
data is "discarded, never persisted". Applied to a completed weight awaiting body
composition, that rule discards a real measurement and inverts its own rationale.
E17's action is therefore **persist the weight-only row**, not discard it. This
keeps the decoder a pure function over bytes while leaving the timeout where the
timers already live.

**Identity and the E9 latch.** Duplicate suppression keys on
`(userIndex, timestamp, raw weight)` — raw, so equality is integer equality and
not floating-point comparison of scaled values. Because the correlator now owns
what "an emission" is, `00-design.md` §2.3 E9's in-session latch moves here from
`GattSession`; leaving it in the session would split one invariant across two
layers.

> **Corrected in the Phase 2 reconciliation (O-03).** This paragraph originally
> read: "A *different* weight frame arriving while one is buffered flushes the
> buffered one weight-only and **starts a new pair**", with the latch stated as
> "at most one emission per `userIndex`, at most two distinct indexes". Starting
> a new pair is the misattribution O-03 names, and it was still live in the code
> this document describes. The sequence: `W1` buffers; `W2` (a second user)
> supersedes it, so `W1` is released weight-only and `W2` becomes pending; then
> `BC1` — user 1's body composition, arriving late — sees a non-null pending
> weight and pairs with `W2`. User 2's row is persisted carrying user 1's body
> fat, muscle, water and impedance, under an index the wrong-user gate reads as
> correct. The Body Composition frame carries no timestamp and no user ID
> (`03-hardware-validation.md` §5), so there is no in-band signal that could
> detect the mis-pairing.
>
> **The latch is now "one emission per session, full stop"** — O-03's own
> recommended option (a). A superseding weight releases the buffered one
> weight-only and **closes correlation**; it does not become the new pending
> weight. Every frame after that, of either kind, is counted
> (`unpairableFramesDropped`) and dropped — never speculatively attached. This
> also closes the same bug's other entry point, which O-03 did not name: after a
> completed pair, a repeated body-composition frame was buffered as an orphan and
> would have paired with whatever weight came next.
>
> `MAX_USERS_PER_SESSION = 2` becomes `MAX_EMISSIONS_PER_SESSION = 1`, and E9's
> "at most 2 distinct userIndexes" plus `00-design.md` §2.1's
> `EMITTED → MEASURING` edge become **unreachable for this decoder**. They are
> marked retired there rather than deleted, on the same footing as
> `StabilityDetector` and `DecodeEvent.Live` in §5 below: correct machinery for a
> scale whose measurement frames are independently attributable, kept for the
> pluggable-decoder goal, dead for the BF720.
>
> The cost is real and accepted: if a household member weighs first and JD second
> inside one session, JD's reading is now lost where the buggy code would have
> kept it. `00-design.md` §8.4's asymmetry decides it — bad Garmin history is
> materially harder to clean up than a missed weigh-in is to redo — and O-03's
> own evidence-against notes the scale most likely powers down between users,
> making two weigh-ins in one BLE session rare or impossible anyway.

### `ScaleReading` field changes

The revision doc's obligation from ADR-002 is to be honest about what the
hardware actually reports. Four fields in `00-design.md` §2.7 do not survive
contact with the SIG profile:

| §2.7 field | Reality | Resolution |
|---|---|---|
| `bodyWaterPct` | The SIG profile reports body water as a **mass** (`36.96 kg` in the capture), not a percentage | `ScaleReading.bodyWaterMassKg` holds the raw SIG value. The percentage is derived at the persistence boundary, where the weight to divide by is known. `ReadingEntity.bodyWaterPct` keeps PRP §5's column name |
| `bmr` | SIG Basal Metabolism is **kilojoules** (`6778 kJ`); PRP §5's `bmr` reads as kcal (`1620`) | `ScaleReading.basalMetabolismKj` holds the raw unit; the kJ→kcal conversion happens at persistence. A conversion is not a decode, and burying it in the parser would make the parser's own test unverifiable against the spec |
| `boneMassKg` | Not a field of the SIG Body Composition profile at all | Retained as nullable, never populated by `BeurerDecoder`. PRP §5 pins the schema and a future non-SIG decoder (openScale-family scales do report bone mass) may supply it |
| `amr` | Active metabolic rate is BMR × an activity factor — a derivation, not a measurement, and not a SIG field | Same treatment as `boneMassKg` |

Four fields are **added**, because the BF720 reports them and PRP §2 is explicit
that nothing is discarded at the point of measurement: `muscleMassKg`,
`fatFreeMassKg` (both flagged unsupported on this unit, so always null — the
frame's own flags say so), `softLeanMassKg`, and `impedanceOhms`. Also
`heightM` and `scaleTimestampMillis`, the latter kept distinct from
`capturedAtMillis` because the scale's clock and the phone's clock are different
facts and the dedup rule (§3.3) keys on the phone's.

## 4. `00-design.md` §9's constants table is superseded

§9 lists `BEURER_SERVICE_UUID`, `BEURER_NOTIFY_CHAR_UUID`,
`BEURER_WRITE_CHAR_UUID`, `INIT_SEQUENCE`, `OPCODE_*` and `WEIGHT_SCALE_FACTOR`
as symbols owed a value in Phase 3, sourced from openScale's Beurer/Sanitas
**wiki page**. That page documents the older proprietary opcode protocol used by
other members of the family. ADR-007 established this unit does not speak it.

**None of those symbols have a referent, and they are not implemented.** Phase 3
WP-05 and `constants-provenance.md` are built on that table and must be rewritten
against `SigWeightProfile.kt`, which replaces it. Left uncorrected, WP-05 would
faithfully fill in values for a protocol this scale does not use — and, worse,
they would look sourced and provenance-commented while being wrong.

Provenance for the replacements follows ADR-002's convention with the primary
source corrected: the **Bluetooth SIG specifications** (Weight Scale Service /
Weight Measurement 0x2A9D, Body Composition Service / Body Composition
Measurement 0x2A9C, User Data Service / User Control Point 0x2A9F, and Assigned
Numbers for the 16-bit allocations and the Base UUID), cross-checked against
openScale's `StandardWeightProfileHandler.kt` and `StandardBeurerSanitasHandler.kt`
(GPL-3.0), reimplemented from protocol understanding, no source copied.

Because the capture is real, these constants are **confirmed, not
`UNCONFIRMED`** — `01-plan.md` §0.1's "constants land early as unconfirmed"
sequencing no longer applies to this file. The confirmation date (2026-08-22) and
the device MAC are in the file header.

The two proprietary services the probe saw (`0xFFFF`, `0xFF00`) remain
unexercised and unimplemented; the standard path produced a full reading without
them.

## 5. Disposition: stabilization detection (`00-design.md` §2.4, RISK-1)

`03-hardware-validation.md` records that the SIG Weight Measurement
characteristic has no final/stabilized flag and simply notifies **once**, when
the scale has a result. Neither branch of §2.4's disjunction describes this
device: there is no flag to read, and there is no stream of unstable frames for a
quiescence heuristic to settle over.

**Disposition: `StabilityDetector` is not on the BF720's live path and is not
implemented in this skeleton.** Consequences that must be carried into Phase 3
rather than discovered there:

- `01-plan.md` schedules WP-03 at position 3 of 31 as RISK-1, ahead of almost
  everything, on the reasoning that a wrong stability decision produces a
  silently wrong reading. That reasoning was sound when written and is now moot
  for this hardware: the scale decides stability, and it does so before it
  transmits. **WP-03 should be rescheduled, not merely re-scoped** — building it
  first for a device that cannot exercise it spends the earliest and most
  valuable slot in the plan on unreachable code.
- `00-design.md` §2.1's `MEASURING → MEASURING` self-transition on "unstable
  frame" is unreachable for this decoder, as is `DecodeEvent.Live`.
- The detector remains *specified* for the pluggable-decoder goal. A v2 Renpho or
  Xiaomi adapter would need it. It should be written when there is a decoder that
  emits `Live`, against that decoder's frames — not now, against synthetic
  samples modelling step-on dynamics nobody has measured.

This is the one place where the Phase 2 pass argues the plan's *ordering* is
wrong rather than its content, so it is flagged for the lead rather than acted on
unilaterally.

> **Resolved.** The lead authorised the re-ranking during the Phase 2
> reconciliation, and `01-plan.md` §1 now carries it: **WP-07 (the UDS
> register/consent handshake) is RISK-1**, WP-03 is RISK-2, demoted to a
> portability and fallback guard and moved out of the strictly-ordered prefix
> into the decode lane after WP-10. HW-08's pass criterion becomes "confirm
> whether any live/intermediate weight indications occur at all" — the
> observation that would restore WP-03 if the single capture behind this
> disposition proves to have been thin evidence for a negative claim.

## 6. Dependencies beyond the ground rule

The ground rule is AndroidX + kotlinx + OkHttp + Room + WorkManager. Two notes:

- **`kotlinx-serialization-json`** is used as a plain runtime library for
  `JsonObject`/`JsonPrimitive` — no compiler plugin, no `@Serializable` classes.
  It is kotlinx, so inside the rule; recorded because `00-design.md` §4.3's
  `ShapedPayload(val json: JsonObject, ...)` needs a `JsonObject` type and
  Android's `org.json` throws in JVM unit tests, which would have forced the
  contract tests onto Robolectric for no benefit.
- Nothing else was added. No DI framework, no Retrofit, no assertion library
  beyond JUnit 4.

**One escalation.** `androidx.security:security-crypto` 1.1.0 ships
`EncryptedSharedPreferences` and `MasterKey` as **deprecated** — the build emits
nine deprecation warnings from `AuthTokenStore.kt` and they are real, not noise.
The agent prompt's ground rule mandates EncryptedSharedPreferences by name, so
the rule and the platform now disagree. This is a decision for JD, not something
to resolve silently: the plausible successors are `androidx.datastore` with an
app-managed keystore key, or Android's `Keystore`-backed encryption directly.
Nothing is blocked in the meantime — the deprecated API works and both the token
and the ADR-007 consent code use it — but the choice should be made before v1
ships rather than after, since migrating a stored token and a stored consent code
is a data migration, not a refactor.

  `BodyCompositionMeasurementParser`, `FrameReader`, `SigWeightProfile`
- `VitalForgeHttpClient`, `ResponseClassifier`, `V1Shaper`, `V2Shaper`
- `DedupPolicy`, the Room schema (exported at `app/schemas/…/1.json`)
- `AuthTokenStore`, `EncryptedConsentStore` (Android-only; JVM tests use an
  in-memory `ConsentStore`, since EncryptedSharedPreferences needs a real
  keystore and a keystore failure would be red for the wrong reason)
- `FakeGattTransport`, with its own tests — 01-plan.md §3 requires them because
  the fake is the foundation for the ~20 fixture-driven packages in §3.4. That
  requirement immediately paid for itself: a zero-replay `MutableSharedFlow`
  silently dropped every event emitted before a collector attached (and
  `tryEmit` returns `true` for a dropped emission, so nothing looked wrong).
  Since a scripted fake emits synchronously from inside `connect()`, WP-06 would
  have presented as a connect timeout with no cause.
